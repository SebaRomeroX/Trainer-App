[ ] 1. IDOR on messages GET endpoint
    File: src/app/api/messages/route.ts (lines 21, 32-46)
    Problem: GET ?with= param lets any user query conversations
             with ANY user. No ownership/authorization check.
    Fix: Validate that otherUserId is the user's trainer or
         one of their assigned clients before querying.

[ ] 2. Access token leaked in JSON response body
    Files: src/app/api/auth/login/route.ts (line 60)
           src/app/api/auth/register/route.ts (line 63)
           src/app/api/auth/refresh/route.ts (line 51)
    Problem: Token returned in body AND set as httpOnly cookie.
             Body access negates httpOnly XSS protection.
    Fix: Remove accessToken from JSON response body. Only use
         httpOnly cookie for transport.

[ ] 3. No refresh token revocation on logout
    Files: src/app/api/auth/logout/route.ts (lines 7-11)
           src/app/api/auth/refresh/route.ts (lines 44-48)
    Problem: Logout only deletes cookies. Stolen refresh tokens
             remain valid for up to 7 days.
    Fix: Add server-side token blocklist (Redis or DB collection)
         or implement refresh token rotation with storage.

[ ] 4. Password reset endpoint is non-functional
    File: src/app/api/auth/reset-password/route.ts (lines 28-34)
    Problem: No reset token generated, no email sent. Returns
             fake success response.
    Fix: Generate a time-limited reset token, store in DB,
         send via email, validate on submission.

[ ] 5. Inconsistent [id] parameter semantics across client routes
    Files: src/app/api/clients/[id]/routine-changes/route.ts (line 20)
           src/app/api/clients/[id]/feedback/route.ts (lines 20-21)
           src/app/api/clients/[id]/ratings/route.ts (lines 24-27)
    Problem: Some routes treat [id] as ClientProfile._id, others
             as User._id. Half the sub-resource endpoints break.
    Fix: Standardize all [id] routes to use ClientProfile._id.
         Look up userId from profile where needed.

[ ] 6. Race condition: non-atomic client creation
    File: src/app/api/clients/route.ts (lines 61-86)
    Problem: User.create + ClientProfile.create not in transaction.
             If profile fails, orphaned User remains.
    Fix: Wrap in MongoDB transaction, or create profile first
         and let User creation fail cleanly.

[ ] 7. Race condition: duplicate routine assignment
    File: src/app/api/routines/[id]/assign/route.ts (lines 55-108)
    Problem: Duplicate check + create are not atomic. Concurrent
             requests create duplicate active assignments.
    Fix: UsefindOneAndUpdate with upsert or add a unique compound
         index on (clientId, routineId, status).

[ ] 8. Race condition: duplicate progressive overload plan
    File: src/app/api/progressive-overload/route.ts (lines 102-128)
    Problem: Same check-then-create pattern as bug #7.
    Fix: Use atomic upsert or unique compound index.

[ ] 9. TOCTOU: stale exercise index in suggestion resolve
    File: src/app/api/progressive-overload/suggestions/[id]/resolve/route.ts
          (lines 76-98)
    Problem: Exercise array index read then used for $set.

[ ] 10. Dashboard loads all data into memory (OOM risk)
